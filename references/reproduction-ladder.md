# 从源码理解到从 0 到 1 复现

## 先决定复现什么

“复现代码”至少有三种不同目标，先写清当前目标：

| 目标 | 成功标准 | 通常不需要 |
|---|---|---|
| 机制复现 | 小规模实现复现论文核心因果与正确行为 | 原项目的服务接口和全部优化 |
| 系统复现 | 完整输入到输出路径在限定配置下可用 | 完全相同的模块组织 |
| 性能复现 | 在记录环境中达到可比较的指标 | 未验证的跨硬件数字 |

默认先做机制复现；只有机制和系统路径正确后，才把性能当作下一个目标。

## 实现阶梯

```text
M0 手算或朴素 oracle
  → M1 单请求、串行的最小主路径
  → M2 核心状态与边界条件
  → M3 batch、生命周期与资源管理
  → M4 必要的低层优化
  → M5 在固定环境下评估性能
```

每一阶都要有输入、预期可观察结果、失败时可定位的状态。若 M1 不能解释或验证，就不要通过阅读更多 kernel 来跳到 M4。

## 每个机制的复现契约

为一个机制写下五项：

1. **输入**：形状、单位、所有权和前置条件。
2. **输出**：内容、顺序、形状和允许误差。
3. **状态变化**：谁创建、更新、失效和释放哪些状态。
4. **不变量**：哪种错误结果必须不可能发生。
5. **oracle**：最小样例如何知道答案正确。

例如，缓存机制的 oracle 不能只看最终吞吐：需要能观察命中、缺失、替换后的映射和读取值是否正确。

## 低层代码的进入条件

进入 CUDA、Triton、通信或异步实现前，先有等价的透明版本。说明：

- 为什么这个机制无法只靠上层实现满足目标；
- kernel 的输入和输出分别来自、流向哪里；
- 数据在 host/device/共享内存中的位置；
- 哪个依赖保证生产早于消费、使用早于释放；
- 优化后与 reference 必须保持哪个观察结果。

性能优化失败时，回到最近可验证的 reference 版本比较状态和输出；不要只凭端到端吞吐猜测错误位置。
